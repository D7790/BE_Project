   "A non-positive discriminant rejects the operating point."
   simulations/hardware_model.py rejects discriminant <= 0, including the marginal
   zero-discriminant point. The equation itself and nominal results are correct.

2. C014: clarify the sampling rates by measurement type.
   Suggested wording: "Electrical acquisition and the policy update run nominally
   at 10 Hz; temperature is refreshed nominally at 1 Hz and reused between updates,
   and telemetry is emitted nominally at 1 Hz."
   firmware/src/main.cpp measures INA219 readings in the >=100 ms branch but reads
   DS18B20 temperature in the >=1000 ms branch. The current blanket statement that
   firmware "samples nominally at 10 Hz" may imply temperature also refreshes at
   that rate. Actual scheduling/peripheral timing has not been measured.

   or "distributed configuration." No physical hardware has been deployed in this
   study. The 3.5 W provisional restoration increment itself is correct.

   checkpoint, rather than implying a fresh rerun of the unchanged script will

   Suggested wording: "The saved publication recheck passed 38 checks before the

OPTIONAL WORDING IMPROVEMENTS

- C014 operating thresholds can be exact without calling them sensor acceptance
  bounds: fan OFF for V <= 11.6 V, V > 14.7 V, or T >= 45 C; |I_battery| > 2 A
  causes invalid-sample handling. The raw plausibility window is broader (8..16 V,
  -10..70 C), and firmware also checks converter-branch current before constructing
  a valid sample. The existing general wording is broadly right but omits these
  boundary distinctions.
- C024 could state explicitly that discharge experiments execute the Python
  reference policy; separate host C++ tests exercise production policy/decoder
  logic. Neither is execution of ESP32 peripherals or the compiled ESP32 binary.
- C026 can make the causality clearer: modeled lower-power losses account for the
  slightly larger total delivered energy; longer controller operation explains
  why more of that delivered energy goes to the controller while lamp-plus-fan
  energy declines. The numerical energy accounting is correct as written.

CONTROL-LOGIC CHECK

Charge sign/efficiency: PASS. Positive battery current discharges; negative current
charges. Effective charging current is 0.98*I, still negative, so subtracting it
in Eq. (1) raises SOC with a reduced charge-counting increment.

Energy/runtime: PASS. Eq. (2) uses nominal 12.8 V, configured 6 Ah and 20% reserve.
Eq. (3) uses unsmoothed load-branch power only when P_U2 > 0.2 W. The separate
battery-power runtime uses alpha=1-exp(-dt/3 s). The manuscript correctly separates
these denominators and notes omitted upstream/internal losses.

Shedding: PASS. Nominal minimum is 3 h; a below-threshold condition must persist
for 3 s. The comparison begins with optional_on=True and known 68% SOC, an explicit
simulation precondition. It does not demonstrate physical synchronization or restore.

Restoration: PASS. Explicit request; hardware must be enabled, sample valid, SOC
known and >20%, temperature <45 C, and 11.6 < V <=14.7 V. Prospective input power
adds provisional 3.5 W when the fan is off. E_hat/P_prospective must be >= minimum
+0.25 h. Firmware accepts serial MIN_H values 0..12 h; controller/model defensive
validation allows 0..24 h. The manuscript does not claim a conflicting range.

Timing/data guards: PASS with sampling clarification above. A non-finite, <=0 or
>2 s integration interval is invalid. Invalid measurements clear charge reference
and keep the optional output off. Unknown reference and build-time hardware lock
also keep it off. Production HARDWARE_CONFIRMED and SOLAR_SENSOR_FITTED are false.

Full-reference procedure: PASS. Reboot does not trust the diagnostic stored SOC.
Operator confirmation additionally checks valid sample, 13.4 <= V <=14.7 V and
|battery current| <=0.10 A. The dedicated button requires a five-second hold;
the serial confirmation command is explicit rather than hold-timed. These checks
do not prove full charge, exactly as the manuscript states.

Python versus firmware: PASS for the reported discharge scope. Python baseline
uses automatic=False; production's zero runtime threshold is the corresponding
user setting. Operating limits remain active. Python accepts a supplied exact
reference while production syncFull sets 100% only after the operator procedure.
Host tests separately cover locked and armed copies; no hardware-armed source
or compile setting was changed by the paper work.
