PROJECT BACKGROUND AND IDENTIFIED PROBLEM

Project Title

WattSense: Battery Monitoring and Priority Load Control

Problem Statement

A battery supplying multiple loads has limited stored energy. Running essential and optional loads continuously can shorten the useful backup period for essential services. Basic battery protection does not necessarily decide which load should receive priority. This project aims to monitor a small battery-powered DC system, estimate available charge and backup time, and disconnect an optional fan when estimated backup becomes insufficient. An essential lamp remains powered. Lamp and fan service times will be compared under matched starting conditions.

Motivation / Need

During limited backup operation, essential services should receive priority. Battery measurement and embedded control can help allocate available energy. A practical demonstrator provides engineering work in sensor calibration, PCB design, firmware, switching and experimental evaluation. A local dashboard makes measurements and decisions visible and records data. The expected benefit is longer essential-lamp service through reduced fan operation; physical tests must establish the actual result.

Existing System & Limitations

A protected battery pack uses a Battery Management System for cell protection, while a compatible charger regulates charging. Simple arrangements may supply all connected loads until an operating limit is reached without prioritising an essential branch. Published energy-management systems already use priority switching and charge estimation, sometimes with forecasting or optimisation. Their batteries, loads and power levels differ from our demonstrator, so their accuracy and runtime results cannot be transferred directly. Current-sensor error, uncertain capacity and an incorrect starting reference affect charge estimation.

Research Gap / Problem Identified

The project addresses a practical need for an affordable teaching prototype that connects calibrated battery measurement with local priority-load control and records the resulting service tradeoff. The focus is integrating a custom interface PCB, estimation, switching and repeatable experiments. Priority switching is an established method. Our contribution will be the implementation and measured evaluation, including essential-lamp runtime, lost fan service, startup behaviour and limitations.

PROPOSED SYSTEM AND OBJECTIVES

Proposed System

The proposed system will use a purchased protected common-port 4S LiFePO4 pack, a supplier-matched charger and an external regulated 5 V buck converter. Nominal pack voltage is 12.8 V. The 6 Ah capacity used in modelling remains provisional.

One custom 100 x 90 mm, four-layer Rev B PCB integrates three INA219 current-sensing channels, shunts, the MOSFET fan switch, branch protection and connectors. An external ESP32 development board reads current, voltage, a DS18B20 temperature probe and local buttons. The essential lamp stays connected; the optional fan has a controlled return path.

The ESP32 estimates state of charge by integrating signed battery current from a valid reference. It starts with unknown charge and the fan OFF. At default settings, estimated backup below 3 hours for 3 seconds switches the fan OFF. Restoration requires an explicit request, valid operating conditions and at least 3.25 hours estimated with the fan included. A measurement gap longer than 2 seconds invalidates the charge reference. The priority runtime estimate assumes no future charging and is not a guaranteed minimum.

USB serial transfers readings to a Python collector and local browser dashboard for display and CSV recording. The ESP32 makes the hardware decision. Physical assembly and measurements are pending. Solar charging may be added later using a compatible controller.

Functional block diagram to draw

Protected battery -> fuse/disconnect -> battery sensor U1 -> system bus -> load sensor U2 -> external 5 V converter -> lamp and switched fan. Charger -> sensor U3 -> system bus. Sensors, temperature probe and buttons -> ESP32 -> fan MOSFET. ESP32 -> USB serial -> dashboard/CSV.

Economic: The current allocation totals Rs 9,700, within the below-Rs 10,000 target. It is a planning ceiling; exact compatible parts and delivered quotations must confirm affordability.

Operational: A four-member team can divide hardware, firmware, measurements and documentation. College lab instruments support bring-up and calibration. Startup testing needs oscilloscope access.

Schedule: Review 3 can present design, software and simulation evidence. Procurement, assembly and measured evaluation are planned before final submission next semester.

Requirements

Hardware: Protected common-port 4S LiFePO4 pack with BMS; matched charger; external 5 V buck; Rev B PCB and specified components; classic ESP32 board; powered DS18B20 probe; small 5 V lamp/fan; buttons; wiring; near-pack fuse/disconnect and mounting.

Software: KiCad; PlatformIO/C++ firmware tools; Python and project dependencies; local browser dashboard; CSV logging; existing electrical and battery/load simulation tools.

Laboratory: Multimeter, adjustable current-limited supply, soldering equipment, independent reference measurements and oscilloscope.

Functional: Valid sensor acquisition; unknown-charge handling; current integration; runtime estimate; fan priority control; controlled restore; fault indication and recording.

Performance targets: Voltage error within +/-1%; current error within +/-(3% of reference + 10 mA). Targets have not been achieved by physical measurements. Intended ceilings to qualify are 2 A on the battery path and 1.5 A total continuous at 5 V. Begin with measured lamp/fan current no more than 0.6 A per branch and qualify startup separately. The lamp requires a supervised external stop at the trial endpoint.

Current status for an attached progress note

Design, firmware, dashboard and simulation work are available. The 30 September recorded audit passed 45 Python tests, 67 host C++ assertions and both firmware builds. In the nominal model, lamp service was 5.48 h in the baseline and 7.88 h under priority control; fan service decreased from 5.48 h to 2.49 h. These are simulation results under stated assumptions. Physical performance remains pending.
